## Config fields

- Offer exactly the settings DigitalOcean offers for that engine. Tuned values (memory, connections) are not fields; `tunedSettings()` renders them and Retune refreshes them.
- Field keys must not contain dots: `UpdateDatabaseConfigRequest` validates `config.<key>`, so a dotted key is read as nested input. Map flat keys to the engine's option paths in the driver (`Mongodb::fileOptionsOf()`), and render only known paths so stale keys from removed fields never reach the engine (mongod refuses unknown options).
- Values arrive as strings. When the config format is typed (YAML/JSON), render numbers as numbers (`JSON_NUMERIC_CHECK`).
- `->restarting()` sends a change through `RedeployDatabase` (rolling restart); dynamic fields go through `config.apply-config` with `scriptData()->liveConfig()` (`settings`, `resets`).
- Settings that are not config-file options (MongoDB's cluster-wide default read/write concern) go to their own `NodeFile` from `configFiles()` and are applied on the primary by `lifecycle.start` and `config.apply-config`, then healed by `lifecycle.status` so they survive failovers and late creation.

## Fixed settings (registration, read through the driver)

| Setter                                                             | Default                                  | Notes                                                                                                                                                  |
| ------------------------------------------------------------------ | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `directory(path)`                                                  | `/srv/<engine>`                          | The bind-mounted data root.                                                                                                                            |
| `systemUser(user)`                                                 | the engine id                            | The engine user inside the image (UID 64999).                                                                                                          |
| `port(port)`, `poolPort(port)`                                     | `ClientPorts::CLIENT`, none              | Client port (25060 for SQL engines and MongoDB, `ClientPorts::KEY_VALUE` for key-value); pooler port.                                                  |
| `peerPorts(ports)`                                                 | `[]`                                     | Extra ports only peers reach (Patroni, etcd, Galera SST).                                                                                              |
| `failoverHint(text)`                                               | empty                                    | Shown when failover cannot be automatic.                                                                                                               |
| `persistenceChoice()`                                              | off                                      | Only for engines with snapshot/append-only choices.                                                                                                    |
| `nodeCertificates(files)`, `publicCertificate()`, `rsaServerKey()` | `ca.crt server.crt server.key`, off, off | File names under `<dir>/tls/`; `server.pem` means a combined cert+key, which also gets the `clientAuth` usage so members can present it to each other. |

Callers read them through the driver (`systemUser()`, `ports()`, `tls()`, `failoverHint()`, `supportsPersistence()`). Actions never name step scripts: they call the server steps on the driver's groups (below). Before a database exists, use `Database::providerFor('<engine>')`. Driver code that needs its own directory or user uses its config-file constants.

## DatabaseDriver contract (`app/DatabaseProviders/Contracts/DatabaseDriver.php`)

`DatabaseDriver` is the only engine contract, named like the server and DNS drivers: changes are verbs, reads are nouns even when they hit the server. Extend `App\DatabaseProviders\Drivers\AbstractDatabaseDriver` and add a static `id()`. The driver is built around its database (`$database->provider()` gives `new <Driver>($database)`), so methods read `$this->database` instead of taking it. Valkey and Redis extend `AbstractSentinelDriver`. The driver describes the engine (identity, config, ports, TLS, versions, connection, environment, limits, node files, processes, engine-specific `scriptVariables()` and `membershipVariables()`); `AbstractDatabaseDriver` itself reads the registration config (`label()`, `ports()`, `tls()`, `versions()`, …); the shared parts live in two traits in `app/DatabaseProviders/Concerns/` (`RendersScripts` for `scriptView()`, `render()` and `shell()`, `ProvidesGroups` for the group accessors and factories). What you do with it lives in six groups in `app/DatabaseProviders/Groups/`, reached from the driver:

| Accessor               | Group             | Methods                                                                                                                                                                         |
| ---------------------- | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `nodes()`              | `EngineNodes`     | `start`, `waitUntilReady`, `reset`, `finishBootstrap`, `status`, `wake`, `applyConfig`, `applyPools`, `syncConfig`, `reloadCertificates`, `metrics`                             |
| `cluster()`            | `EngineCluster`   | `cluster`, `uncluster`, `failoverTo`, `forceQuorum`, `quorum`, `admit`, `adopt`, `cloneDonorFor`, `membershipChangesFor`, `updateMembership`, `forget`, `rejoin`, `recoveryPosition` |
| `accounts()` (or null) | `EngineAccounts`  | `createDatabase`, `deleteDatabase`, `createUser`, `updatePassword`, `updatePasswordEncryption`, `deleteUser`, `runSql`, `reservedUsers`, `reservedDatabases`, `passwordEncryption`, `defaultAccountSql` |
| `archive()` (or null)  | `EngineArchive`   | `files`, `variables`, `restoreSource`, `restore`, `status`                                                                                                                       |
| `migration()` (or null) | `EngineMigration` | `form`, `check`, `start`, `progress`, `follow`, `stop`                                                                                                                         |
| `scriptData()`         | `EngineScriptData` | `for`, `versions`, `starting`, `readiness`, `clustering`, `admission`, `stopping`, `deploy`, `archiving`, `restoring`, `liveConfig`, `workspace`, `certificates`, `tlsFiles` |

**Server steps** are implemented once in the group base classes: each picks its node, renders the engine's step script (`$engine->scriptView()`) and runs it as one named `ServerLog` with `EngineGroup::runStep()`. Skipping is explicit: a step only one engine has is a no-op in the base group and its owner overrides it to run the script (`SentinelNodes::reset()`, `PostgresNodes::syncConfig()` / `applyPools()`); an engine without a step overrides it as an empty method in its group subclass (`SentinelNodes::finishBootstrap()`, `MariadbNodes::wake()`, `MongodbCluster::cluster()` / `admit()`, `MysqlCluster::admit()` / `updateMembership()` / `rejoin()` and `recoveryPosition()` returning `null`, `MariadbCluster::adopt()` / `forget()`, `SentinelCluster::admit()` / `adopt()` / `forget()`). There is no implicit skip: a missing script throws `MissingEngineScript`. Groups take their data from `scriptData()` (`$this->engine->scriptData()->starting($node, ...)`) and reach another group only through the driver. Actions keep loops over nodes, order, the operation lock and status refresh.

**Customising a group:** override its protected factory on the driver (`nodeSteps()`, `clusterSteps()`, `accountSteps()`, `archiveSteps()`, `migrationSteps()`, `scriptDataSteps()`) and return a `final readonly` subclass from the engine folder, built with `new <Group>($this, $this->database)`. Defaults: the generic `EngineNodes`, `EngineCluster` and `EngineScriptData`, no accounts, no archive, no migration. Existing overrides: `MysqlCluster` / `MariadbCluster` (`cloneDonorFor`), `PostgresCluster` / `MariadbCluster` (`membershipChangesFor`), the skipped steps above (`PostgresNodes`, `MariadbNodes`, `MongodbCluster`, `Shared\SentinelNodes`, `Shared\SentinelCluster`), `<Name>Accounts` (reserved names, `passwordEncryption`), `<Name>Archive`, `<Name>Migration`. Narrow the factory's return type (`protected function archiveSteps(): MysqlArchive`) when the driver itself calls engine-only methods such as `schedules()` in `processes()`.

**What a new engine writes:** its Blade steps and these methods.

| Method                                         | Notes                                                                                                                                                                                                 |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `connection()`, `environment($endpoints)`      | What the UI shows and the env vars apps get. Use `DefaultAccount::environment()` for the `DB_*` keys.                                                                                                 |
| `processes($node)`                             | `ProcessManifest` of `ProcessSpec`s and `Schedule`s, rendered to `/srv/<engine>/conf/processes.json`. HA processes only appear once the database has a peer; backup agents only while recovery is on. |
| `configFiles($node)`                           | Every `NodeFile` to write on deploy (config, secrets as `NodeFile::secret`, keyfiles owned by the engine user with mode 600). Read the server's size with `NodeResources::of($node->server)`.         |
| `fields()`, `tunedSettings($resources)`        | Defaults + tuned values + user overrides are merged in `scriptData()->liveConfig()`.                                                                                                                 |
| `generateSecrets()`                            | Generated once at create, stored encrypted in `DatabaseSettings`. Include `DefaultAccount::secrets()` when the engine manages accounts.                                                               |
| `role($output)`                                | Parse the status script into `NodeRole`.                                                                                                                                                              |
| `maxReadOnlyNodes()`                           | The engine's real replica limit (PostgreSQL: WAL senders and slots; MongoDB: 50 replica set members; MySQL/MariaDB/Valkey/Redis: the primary's connection limit via `primarySetting()`).                |
| optional: `clientAddress($node)`, `canFailover($nodes)`, `scriptVariables()`, `membershipVariables()`, `maxStandbys()` | Defaults: `ip:client port`, three members, no extra variables, 2 standbys.                                                                             |
| accounts, archive, migration                   | See [capabilities](capabilities.md).                                                                                                                                                                  |

## Processes

- Don't set environment the image already sets; the manifest's `env` overrides the container's.
- Guard the server process on its data directory (`sh -c '[ -d <dir>/data ] || exit 0; exec <server> …'`): after an erase or a lost disk the wrapper can start the engine before `lifecycle.prepare` recreates the directory, and it then loops on restarts until `wait-ready` fails the deploy.
- Use `ProcessSpec`/`Schedule` DTOs with argv lists; `sh -c` only where a value must be read from a secret file at start (`MongodbArchive::agentProcess()`), so no password lands in the manifest.

## Writing style

- Logic about one model lives on that model (`$database->primaryServer()`, `$node->certificateFits()`, `$server->markProvisioned()`); actions only orchestrate and never write `update([...])` state changes or re-query relations themselves.
- Model ids are UUIDv7 strings: type them `string`, validate them with `uuid`, never cast them or treat them as numbers.
- Driver methods are short and delegate to collaborators (migrators, DTOs, Blade templates). `configFiles()` is a list of `NodeFile::config()`/`NodeFile::secret()` entries whose content is `$this->render('files.<name>', [...])`, plus inline values for single-value files. Shell commands for process specs live in `processes/<name>.blade.php` and become argv with `$this->shell('<name>')`. Paths used outside templates stay constants on the driver (`Mysql::ROOT`, `Mysql::CONFIG`).
- Use `NodeFile` named constructors; never build raw arrays for files.
- Add precise PHPStan types (`list<NodeFile>`, `array<string, string>`, array shapes); never silence PHPStan.
